## 들어가기 전에

여러 팀이 함께 작업하는 프로젝트에서 Git을 사용하다 보면 커밋 히스토리가 복잡해지고 병합 충돌이 자주 발생하는 문제를 겪어보신 적이 있으신가요?

저희 회사에서는 프로젝트를 시작할 때 `main` 브랜치에서 `project/프로젝트명` 브랜치를 생성합니다. 이 브랜치에서 프로젝트가 완료될 때까지 모든 팀원이 함께 작업하며 릴리스 직전에 main 브랜치로 병합하는 방식을 사용하고 있습니다. 하지만 문제는 다른 팀들도 동일한 시점에 릴리스를 준비하며, 동시에 병합을 시도하다 보니 충돌이 빈번하게 발생한다는 점입니다. 이러한 상황은 커밋 히스토리를 복잡하게 만들고, 병합 과정에서 많은 시간을 소모하게 만듭니다.

이 글에서는 저희 팀이 겪은 문제점과 이를 해결하기 위해 학습한 Git Merge 전략을 공유합니다. 복잡한 커밋 히스토리를 깔끔하게 관리하고 효율적인 병합을 실현하기 위한 내용을 소개합니다.

## 병합(Merge)을 수행하는 세 가지 방법

Merge, Squash, Rebase 세 가지 방법에 대해 특징과 사용 시기를 간단히 정리해 보겠습니다.

### 1. Merge Commit

기본 병합 방법으로, 두 브랜치를 병합하면서 별도의 병합 커밋이 생성됩니다.

- **장점** : 각 브랜치의 히스토리를 온전히 보존할 수 있습니다.
- **단점** : 커밋 그래프가 복잡해질 수 있습니다.
- **적용 상황** : 병합 후에도 브랜치 간 작업 내용을 추적해야 하는 경우. 예를 들어, 여러 개발자가 동시에 작업한 내용을 통합할 때 유용합니다.

### 2. Squash Merge

브랜치를 병합하면서 모든 커밋을 하나의 커밋으로 합칩니다.

- **장점** : 여러 커밋을 하나로 합치기 때문에 그래프가 깔끔하고 가독성이 좋습니다.
- **단점** : 여러 커밋이 하나로 합쳐지기 때문에 상세한 변경 내역을 추적하기 어려울 수 있습니다.
- **적용 상황** :
  - **PR(Pull Request) 코드 리뷰 시 자잘한 수정사항이 많을 때**:
    - 예를 들어, 기능 개발을 완료하고 PR을 올렸는데 리뷰어의 피트백에 따라 작은 수정사항이 여러 번 발생할 수 있습니다. 이때 `Squash Merge`를 사용하면 모든 수정사항을 하나의 커밋으로 통합해 깔끔한 히스토리를 유지할 수 있습니다.

### 3. Rebase Merge

내가 작업한 커밋들을 다른 브랜치의 최신 상태 위로 "재배치"하는 작업입니다.

- **장점** :
  - 브랜치의 커밋 히스토리를 깔끔하게 유지할 수 있습니다.
  - `Rebase`를 사용하면 커밋들이 마치 한 줄로 쭉 나열된 것처럼 보입니다.
- **단점** :
  - 원격 저장소에 올라간 브랜치에 대해 리베이스를 사용하면 다른 개발자의 작업에 영향을 줄 수 있습니다.
  - 리베이스 과정에서 충돌이 발생하면 각 커밋마다 충돌을 해결해야 하므로 번거로울 수 있습니다.
- **적용 상황** :
  - **내 작업을 최신 상태로 유지하고 싶을 때**:
    - 예를 들어, `main` 브랜치에서 분기한 `feature/login` 브랜치를 작업 중인데 다른 팀원들이 `main` 브랜치에 새로운 코드를 추가했다면 `Rebase`를 사용해 `feature/login` 브랜치를 `main` 브랜치의 최신 상태 위로 재배치할 수 있습니다.
  - **PR(Pull Request)을 보내기 전에 히스토리를 정리하고 싶을 때:**
    - PR을 보내기 전에 Rebase를 사용해 커밋 히스토리를 깔끔하게 정리하면 리뷰어가 코드를 더 쉽게 이해할 수 있습니다.

## 우리 회사 프로젝트에서의 문제점

### 문제점 1: 주기적으로 develop 및 main 브랜치에 병합하지 않음

`project/프로젝트명` 브랜치에서 작업이 지속되면서 주기적으로 `develop` 또는 `main` 브랜치와 동기화하지 않는 문제가 있었습니다. 이로 인해 병합 시 충돌이 더 빈번하게 발생하고 병합 과정에서 많은 시간을 소모했습니다.

### 문제점 2: 큰 프로젝트 브랜치를 develop에 Squash Merge

한 프로젝트의 모든 작업이 `project/프로젝트명` 브랜치에 커밋이 되고 이를 Squash Merge 방식으로 develop에 병합하는 방식이었습니다. 결과적으로 작업 히스토리가 사라지고 문제를 추적하기 어렵게 되었습니다.

## 해결 방안

### 1. local -> project 브랜치에 병합할 때

- **Rebase 사용하기**: 팀원 개개인이 자신의 작업 브랜치를 `project/프로젝트명` 브랜치에 병합할 때 Rebase를 사용합니다. 이를 통해 `project` 브랜치의 히스토리를 선형으로 유지하고 충돌을 최소화할 수 있습니다.

### 2.project -> develop 브랜치에 병합할 때

- **방법 1: `prject` 브랜치를 없애고 feature 단위로 병합**

  - `project/프로젝트명` 브랜치를 없애고, 각 기능(Feature) 단위로 `develop` 브랜치에 Rebase 및 병합합니다.

- **방법 2: `project` 브랜치를 유지하고 주기적으로 Rebase**
  - `project/프로젝트명` 브랜치를 유지하면서, 주기적으로 develop 브랜치에 Rebase하여 동기화합니다.
  - 이 경우에는 이미 원격 저장소에 올라간 브랜치를 리베이스해야 하므로 force push가 불가피합니다. 따라서 이 작업을 진행할 때는 모든 팀원들에게 사전에 공유하고 동의를 얻어야 합니다.

## 결론

우리 회사는 7~8개의 팀이 하나의 리포지토리에서 동시에 작업을 하고 있습니다. 또, 배포일이 정해져 있어 미리 배포하는 것이 절대 금지되어 있습니다. 이러한 환경에서는 각 팀이 feature 단위로 develop 브랜치에 병합하는 것이 현실적으로 어렵습니다.
기존에는 `project` -> `develop` 브랜치에 병합할 때 **스쿼시 머지(Squash Merge)** 를 사용했습니다. 이는 커밋 히스토리를 깔끔하게 유지하려는 목적이었지만 오히려 문제를 야기했습니다. 스쿼시 머지는 여러 커밋을 하나로 합치기 때문에 이후에 특정 변경 사항을 추적하거나 문제를 디버깅하기가 어려웠습니다.

이러한 문제를 해결하기 위해 **방법 2**를 선택했습니다. 프로젝트 브랜치를 유지하면서 주기적으로 `Rebase`를 통해 `develop` 브랜치와 동기화하면 커밋 히스토리를 깔끔하게 유지할 수 있고, 각 커밋의 변경 내역도 명확히 확인할 수 있습니다. 단, Rebase 후에는 `force push`를 사용해야 하기 때문에 모든 팀원과 사전에 충분히 협의한 후 진행해야 합니다.
